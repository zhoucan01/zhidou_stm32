# AT32F415 OTA Bootloader 与 Python 上位机

AT32F415 固定运行区 A + 备份区 B OTA Bootloader（C，Keil 工程）+ Windows 桌面 OTA 上位机（Python tkinter）。

- **Bootloader**：上电约1秒等待握手；收到查询后停留等待控制。开始 OTA 时将有效 A 备份到 B 并校验，再擦除 A、逐包下载到 A。每次启动先校验 A 的 SHA-256，失败则从有效 B 恢复 A；只跳转 A。
- **上位机**（[AT32_OTA_PC/](./AT32_OTA_PC/)）：导入任意 BIN → 自动二次打包（版本区 + SHA-256区）→ 自定义 Modbus 协议逐帧下发 → 串口收发 HEX 与字段解析全部打印 → 内置测试模式。

## 当前 A 运行 / B 备份机制

本节替代下文历史说明中的“翻转分区标志、直接跳转 B”。旧标志扇区不再决定启动位置。

- A：版本 `0x08003800`、SHA-256 `0x08003C00`、原始 APP `0x08004000`；长度记录 `0x08011800`。
- B：版本 `0x08011C00`、SHA-256 `0x08012000`、备份 BIN `0x08012400`；长度记录 `0x0801FC00`。B 只用于存储，不直接执行。
- APP 必须链接到 **`0x08004000`**，SystemInit 的向量偏移也应指向此地址。原始 BIN 最大55296字节，上位机封装格式仍为1KB版本+1KB摘要区+原始BIN。
- 长度记录位于原缓冲扇区：偏移0是有效标记 `0x53484132`，偏移4是原始 BIN 长度（均为芯片小端32位值）。先写长度，最后提交标记。下载未完成不会被当作有效固件。
- 操作码 `1`：A 有效时先擦 B、复制 A 到 B 并校验，成功才擦 A。A 无效时保留现有 B，允许重新下载。两区均无效也可通过 OTA 重新安装。
- 操作码 `2`：先回8字节控制确认，发送完成后重启；新增操作码 **`3`：手动回滚**，先校验 B，成功才覆盖 A；完成后发送原8字节控制成功应答，再从 A 启动。B 无效时不擦 A，返回14字节状态帧。
- A 启动校验失败，自动检查 B 并恢复；恢复写入失败停留 Bootloader。两区都无效时 OTA 状态为 **`0x0055`**，每100ms按现有14字节 `0x10` 查询应答格式主动上报，仍可查询、开始下载或回滚。有效 B 存在但 Flash 恢复失败时状态为0，不误报双坏。
- 逐包 `0x01` 仍仅代表包写入成功，不代表完整固件 SHA-256 成功；摘要不符时不会提交 A，将由启动阶段恢复 B。备份/恢复失败不会发送控制成功确认，状态帧用于报告当前状态。

**旧版迁移：**旧固件没有上述长度记录，无法在重启后可靠确定 SHA-256 范围，因此不会直接启动或备份。首次使用请用新版上位机重新 OTA 安装 A（或烧录完整封装镜像并写入正确长度记录）；第一次成功安装前没有可用备份，下一次升级时才会生成 B。已有按 B 地址链接的旧固件不能作为本方案的备份。

## 快速开始

### 1. 安装上位机

Python 3.10+，在 `AT32_OTA_PC/` 目录：

```powershell
python -m pip install -r requirements.txt
python app.py
```

### 2. 固件校验格式

无需生成密钥或烧录公钥。上位机计算完整原始 BIN 的 SHA-256，写入原SHA-256区前32字节；该1KB区域其余992字节填零。设备端计算相同范围的摘要并比较。

此格式只核对完整性，不提供数字签名或来源认证。旧签名镜像需要重新生成。

### 3. 升级流程

1. 连接串口（默认 1000000-8-N-1，与当前设备的 1M 配置一致）。
2. 复位芯片使其停留在 Bootloader 窗口（上电后 约5秒 内需收到查询帧）。
3. 导入 BIN → 填版本号 → **生成封装BIN**（可选导出）。
4. **查询OTA状态**（必须！Bootloader 等待期只消费查询帧，控制帧会被静默丢弃）。
5. 状态为「空闲」后点 **开始OTA**：自动发送 op=1 握手 → 擦除分区（按设备实际耗时）→ 从包号 0 逐包下发 → 每包等应答 0x01。
6. 末包成功后设备自行校验SHA-256：通过则翻标志重启进新 App；失败则无任何反馈，旧 App 继续运行。

## 协议详解（字节级）

新增站号2的自定义 `0x11` 版本分块查询：Bootloader 和 APP 均读取 `0x08003800` 的 OTA 版本区，并分别返回运行模式0/1。上位机增加版本查询与持续压力测试，自动递增版本、升级后核对APP版本，直到手动停止；详细协议、日志及使用方法见 [上位机说明](AT32_OTA_PC/README.md#版本查询与持续压力测试)。

从机地址 `0x02`。寄存器 `0x00E6`。**普通字段大端，CRC16 小端，CRC32 大端**。

### 0x10 查询请求（14 字节，上位机 → 设备）

| 偏移 | 大小 | 字段 | 值 |
| --- | --- | --- | --- |
| 0 | 1 | 从机地址 | `0x02` |
| 1 | 1 | 功能码 | `0x10` |
| 2 | 2 | 寄存器起始 | `0x00E6` |
| 4 | 2 | 寄存器数量 | `0x0003` |
| 6 | 2 | OTA 状态 | 设备忽略，填 0 |
| 8 | 4 | 会话 key | 设备忽略，填 0 |
| 12 | 2 | CRC16 | 小端，覆盖 0..11 |

### 0x10 查询应答（14 字节，设备 → 上位机）

| 偏移 | 大小 | 字段 | 值 |
| --- | --- | --- | --- |
| 0..5 | 6 | 回显请求前 6 字节 | |
| 6 | 2 | OTA 状态 | 见状态表 |
| 8 | 4 | 会话 key | 当前生效 key |
| 12 | 2 | CRC16 | 小端 |

**OTA 状态**：`0` 禁止升级 / `1` 空闲 / `2` 下载中 / `3` Flash 操作中 / `0x55` 两区固件均损坏（每100ms主动上报）。

### 0x10 控制请求（20 字节，上位机 → 设备）

| 偏移 | 大小 | 字段 | 值 |
| --- | --- | --- | --- |
| 0 | 1 | 从机地址 | `0x02` |
| 1 | 1 | 功能码 | `0x10` |
| 2 | 2 | 寄存器起始 | `0x00E6` |
| 4 | 2 | 寄存器数量 | `0x0004` |
| 6 | 4 | 数据字节数 | `0x00000008`（大端 4 字节字段） |
| 10 | 2 | OTA 状态 | 填 1 |
| 12 | 4 | 会话 key | 本会话 32 位密钥（建议时间戳） |
| 16 | 2 | 操作码 | `0` 无操作 / `1` 开始OTA / `2` 重启 / `3` 手动回滚 |
| 18 | 2 | CRC16 | 小端，覆盖 0..17 |

### 0x10 控制应答（8 字节）

`02 10 00 E6 00 04 CRC16Lo CRC16Hi`（回显地址/功能码/寄存器/数量 + CRC16 小端）。

**操作码行为**（main.c 状态机）：

- `op=1`（开始OTA）：置状态3 → 暂停接收 → 有效A备份至B并校验（A无效则保留B）→ 擦除A → 保存会话key → 恢复接收、置状态2 → 回8B确认。失败回14B当前状态，不回控制成功。
- `op=2`（重启）：先回复8字节控制确认，等待串口发送完成、RS485释放后复位；发送失败保留请求继续重试。
- `op=3`（手动回滚）：校验B → 擦除A并复制B → 校验A并提交长度记录 → 回8B确认 → 从A启动；失败回14B状态。
- Bootloader 等待期约1秒，支持查询或直接控制；查询后停留握手状态等待操作。

### 0xAA 固件数据帧（上位机 → 设备）

`L1` = 本包固件数据长度（≤1024），帧长 `L = 22 + L1`，须 `23 ≤ L ≤ 1046`。

| 偏移 | 大小 | 字段 | 值 |
| --- | --- | --- | --- |
| 0 | 1 | 从机地址 | `0x02` |
| 1 | 1 | 功能码 | `0xAA` |
| 2 | 2 | 帧数据长度 L | 大端，`22+L1` |
| 4 | 2 | 协议号 | 当前固件固定 `0x0001` |
| 6 | 4 | 会话 key | 与握手一致 |
| 10 | 2 | 数据长度 L1 | 大端 |
| 12 | 2 | total_packets | **末包包号 = 包数-1**（见下文包序） |
| 14 | 2 | 当前包号 | **从 0 开始** |
| 16 | L1 | 固件数据 | |
| 16+L1 | 4 | CRC32 | 大端，**仅覆盖固件数据** |
| 20+L1 | 2 | CRC16 | 小端，覆盖 0..19+L1 |

### 0xAA 数据应答（7 字节）

| 偏移 | 大小 | 字段 | 值 |
| --- | --- | --- | --- |
| 0 | 1 | 从机地址 | `0x02` |
| 1 | 1 | 功能码 | `0xAA` |
| 2 | 1 | 应答码 | 见下表 |
| 3 | 2 | 包号 | 大端（成功=本包号；3/7/8=出错帧包号） |
| 5 | 2 | CRC16 | 小端 |

**应答码**：

| 码 | 含义 | 触发条件 |
| --- | --- | --- |
| 0x01 | 写入成功 | 包校验全过并写入 Flash |
| 0x02 | 固件 CRC32 错误 | 数据 CRC32 不匹配 |
| 0x03 | 接收超时 | 收到 ≥16B 的 `02 AA` 残帧，3.5ms 静默后登记 |
| 0x04 | 协议版本错误 | 协议号 ≠ 1 |
| 0x05 | 密钥错误 | key ≠ 握手 key |
| 0x06 | 包序不连续 | 包号 ≠ currentPackage |
| 0x07 | 帧 CRC16 错误 | 0xAA 帧 CRC16 校验失败 |
| 0x08 | 长度异常 | 帧过长、镜像超出56KB分区或末包累计长度不足2056字节 |
| 0x09 | Flash操作失败 | 固件编程、长度记录提交或读回确认失败；不盲目跳转 |

设备校验顺序：协议号 → key → 包号 → CRC32 → 长度 → Flash 写入。
0x10 帧 CRC16 错误静默不回复；CRC32 算法与标准 zlib.crc32 一致。

## 包序规则（关键！）

以 `bootloader/project/app/upgrade.c` 实际代码为准：

- `currentPackage` 为 static，**从 0 开始**；
- 收到包号等于 `currentPackage` 的包并写入成功后应答 0x01 并 `currentPackage++`；
- 结束条件是 `currentPackage > total_packets`。

因此：

| 固件大小 | 包数 | 包号序列 | total_packets 字段填 |
| --- | --- | --- | --- |
| 1024B | 1 | 0 | **0** |
| 2050B | 3 | 0,1,2 | **2** |
| 任意 N 包 | N | 0..N-1 | **N-1** |

即 **首包号必须为 0，total_packets 字段 = 包数 - 1 = 末包包号**（不是总包数）。
上位机已按此实现，GUI 中「首包号」默认 0。

## 固件二次打包格式

最终镜像（设备烧写视图）：

```
偏移 0x000000  ┌────────────────────────┐
              │ 版本区 1KB             │  UTF-8 版本号 + 0x00 零填充
              │ （写入 APPxDATA1）     │
偏移 0x000400  ├────────────────────────┤
              │ SHA-256区 1KB             │  32B SHA-256 摘要 + 0x00 零填充
              │ （写入 APPxDATA2）     │
偏移 0x000800  ├────────────────────────┤
              │ 原始 BIN               │  写入 MSPx_ADDR 起
              │ ...（≤55296B）         │
              └────────────────────────┘
```

**校验内容（关键）**：设备 `verify_firmware(MSPx_ADDR, binSize-2048, APPxDATA2)` 从
原始 BIN 写入起点读取 `len(bin)` 字节计算 SHA-256。PC 端计算相同的完整 BIN：

```text
hash  = SHA-256( bin )                   # 32 字节
APPxDATA2[0:32] = hash                 # 原签名区域保存32字节摘要
```

上位机 `firmware_pack.py` 固定计算完整 BIN，不跳过开头，不补尾部数据。旧签名镜像需要重新打包。

### 容量限制

Bootloader物理分区及原有链接范围仍为13KB（扇区0..12，`0x3400`），Keil启用按体积优化，
不额外设置12KB链接限制；OTA标志和应用地址不变。
本轮全量编译实际Flash占用10,440字节，距13KB边界剩2,872字节。
优化可能使部分局部变量在调试器中不可见，运行逻辑及安全检查不变。

每个镜像分区（扇区 14..69 或 71..126）共 56KB 含 2KB 头 → **原始 BIN ≤ 55296 字节**。

### 设备端SHA-256校验流程

末包写入后：按本次开始OTA时确定的目标进行SHA-256计算并比较 →
摘要不一致：保留原标志，发出本包写入确认后跳回旧应用；一致：擦写扇区13并读回确认新标志，再发应答并跳转。标志提交失败返回09，停留Bootloader。

OTA 分区标志统一为：`1` 跳转分区1，`2` 跳转分区2。当前标志为1时，升级写入分区2，成功后保存2；当前标志为2时，升级写入分区1，成功后保存1。旧编码的0/1标志需按实际有效应用重新设置，不能直接沿用旧含义。

擦除态 `0xFF` 在跳转和升级选择时等同分区1：升级擦写、校验分区2，成功后才保存标志2；失败保留 `0xFF`，后续跳转仍选择分区1并检查应用向量。读取函数返回 `uint8_t`，保留原始 `0xFF`，不提前初始化Flash标志。

## 上位机实现与设备端对照

| 上位机 | 设备端 | 一致性 |
| --- | --- | --- |
| `protocol.query()/control()` 字段偏移 | `wk_usart.c mb_store_frame` + `modbus.c modbus_read_10` | ✓ |
| 包号从 0、total=包数-1 | `upgrade.c appUpgrade()` currentPackage/结束条件 | ✓ |
| 哈希 `sha256(bin)` | `upgrade.c verify_firmware()` 从 MSPx_ADDR 读取完整 BIN | ✓ |
| `reset()` 等待控制确认 | modbusdeal 发完8B确认后复位 | ✓ |

当前生效路径：`wk_usart.c 组帧入队 → main.c 状态机 → upgrade.c 业务处理 → modbusdeal() 发应答`。
开始或重新开始OTA统一调用 `appUpgradeStart()`，先将有效A备份至B，再擦除A，并在成功后清零包号、长度和偏移。
原回调式库状态机和 `modbus_port_poll()` 已移除。

## FAQ

**Q: 开始OTA没有反应？**
必须先点「查询OTA状态」——Bootloader 约5秒 等待窗口内只消费查询帧，控制帧会被丢弃。
且需在窗口期内完成第一次查询，否则设备直接跳旧 App。

**Q: 握手发出后长时间无应答？**
op=1 触发擦除 56 个扇区，期间设备关 RS485 接收并置状态 3，完成后才回复；等待时间使用界面的“查询/握手/数据应答超时(秒)”，不再强制至少15秒。请在操作前设置，运行中的任务保持启动时的值。

**Q: 发送重启指令后上位机报超时？**
新版 op=2 返回8字节控制确认，发完后复位；上位机使用界面超时设置等待。旧Bootloader不会回复，需要同步更新。

**Q: 升级完设备直接进了旧程序？**
SHA-256校验失败时设备跳回旧 App。请确认原SHA-256区前32字节与完整原始BIN的摘要一致，固件哈希起点为 `MSPx_ADDR`，长度为原始BIN长度，并核对应用链接地址。

**Q: total_packets 到底填多少？**
末包包号 = 包数-1。3 包固件填 2。填成包数会导致 `currentPackage > total_packets` 永远不成立，升级永不结束。

**Q: 收到应答 0x03 / 0x07 / 0x08 是什么？**
0x03=半帧 3.5ms 超时、0x07=帧 CRC16 错、0x08=帧或整镜像长度异常。多为串口受干扰或波特率不匹配；0x07/0x08 时设备登记的包号取自残帧偏移 14。

**Q: 上位机会自动重传吗？**
不会。超时后任务停止并提示，避免应答丢失时重复写 Flash 造成包号错位。重新点击「开始OTA」会显式发送新的开始指令，重新擦除目标分区并清零会话，从包号0重来；不会续写旧偏移。

**Q: 固件最大多大？**
原始 BIN ≤ 55296B（56KB 分区 - 2KB 头）。超限请在链接脚本调整分区或压缩应用。

**Q: 会话 key 用什么？**
任意 uint32，GUI 默认填当前 Unix 时间戳。握手与每个数据帧必须一致。

## UART5 Bootloader 调试日志

UART5：PC12为TX、PD2为RX，115200/8N1。USB串口模块RX接PC12并共地，日志为英文ASCII文本。

默认使用英文说明和十进制包号，不再要求根据英文标签和十六进制数字判断指令：

```text
Waiting for handshake
RX: query OTA status
TX OTA status 1
RX: start OTA
Preparing OTA
Backup A to B
TX control ACK
RX packet/last 7/193
TX ACK packet 7
WRITE OK
SHA256 PASS
Starting APP in A
```

操作码2显示“RX: reboot”，确认发完后显示“Reboot ACK sent; resetting”；操作码3显示“RX: rollback”，并显示恢复方向和结果。接收出错会提示CRC16 error count；错误应答直接显示“ERROR: packet sequence”“ERROR: payload CRC32”“ERROR: Flash write”等原因。

“发送…”仅在USART3实际发送成功后输出，不把登记应答当成发送完成。日志在普通上下文输出，中断内只记录信息。

`bootloader/project/app/boot_log.h` 中 `BOOT_LOG_ENABLED=0` 可关闭日志，`BOOT_LOG_VERBOSE=1` 可附加原始帧HEX、CRC数值、完整SHA摘要和写入地址；详细模式会增加Flash占用，开启后需检查链接空间。`BOOT_LOG_PAYLOAD_BYTES` 控制详细模式载荷预览长度，默认16字节。
