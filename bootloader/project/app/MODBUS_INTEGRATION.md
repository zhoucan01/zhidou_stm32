# Modbus DMA 接收与寄存器缓存

## 当前编译体积约束

Bootloader物理空间和原有链接范围为13KB（0x3400），Keil按体积优化，
不额外设置12KB链接限制。OTA标志仍在0x08003400。
全量编译实测占用10,440字节，剩余2,872字节；未删除协议或Flash安全检查。

## 本轮 OTA 修复后的调用规则

- `main.c` 和升级中的重新开始指令均调用 `appUpgradeStart(key)`；不再各自实现擦除分支。
- 标志1/0xFF升级分区2，标志2升级分区1，目标和原标志在本次开始时确定。
- 擦除前通过 `modbus_port_pause_rx()` 关闭DMA、USART事件和接收，清理旧帧及错误队列；所有擦除出口都会恢复通信。
- 开始成功后清零 `currentPackage`、`totolAddr`、`binSize` 和本包缓存；不锁定首包的total字段。
- 每次写入前检查累计镜像不超过57344字节；末包累计至少2056字节，避免减去2048时下溢。
- 整包编程成功才增加包号、累计长度和偏移；部分写入失败返回09，结束本次接收，新的开始指令会重新擦除。
- 固件校验通过后，检查扇区13擦除、标志编程和读回结果。提交失败返回09并停留Bootloader，不返回本包01确认或盲目跳转。
- 本包01仍表示本包数据写入成功；完整SHA-256不一致仍保持原标志，确认本包后进入旧应用。
- 上位机限制原始BIN为8..55296字节；在线设备测试只包含查询、操作码0和再次查询，已移除错误key开始指令及AA错误注入。
- 用户主动重新开始允许从状态2发起；不自动重传或续写旧会话。

验证方式：在工程根目录运行 `python -m pytest -q`。Flash模型直接编译当前升级业务，
覆盖目标选择、擦除失败、短镜像、累计越界、部分写入失败、重新开始和标志提交失败；
DMA/USART模型覆盖暂停时禁止重启DMA、恢复、旧队列清理、拼帧和03/07/08应答。
模型不能替代实际芯片的Flash时序、写保护和断电测试。

## 当前 OTA 分区标志

`1` 表示分区1，`2` 表示分区2；`0xFF` 保持原值，但选择时按分区1处理。
标志为1或0xFF时，升级擦写并校验分区2，成功后保存2；标志为2时升级分区1，成功后保存1。
擦除、写入、SHA-256校验失败不提交新标志；0xFF的应用跳转仍选择分区1并校验向量。
已移除握手分支里强制 `eraseOk=1` 的调试覆盖，擦除失败不会回复开始OTA成功确认。

## 固定协议上下文精简

当前初始化使用 `modbus_port_init()`，不再传入配置和存储回调。
`modbus_t` 只保留会话密钥 `key` 和本地状态 `status`，在 AT32 上占 8 字节。
普通字段和 CRC32 大端、CRC16 小端、单包固件上限 1024 字节均固定。

原配置初始化、回调式自动 OTA 处理及 `modbus_port_poll()` 已移除；
后文涉及旧配置/回调/自动处理接口的内容为历史记录，不作为当前调用方式。
主循环仍通过两个取包接口消费接收队列，由 `appUpgrade()` 执行业务、
`modbusdeal()` 发送应答和处理有效重启请求。

微库下实测 Flash 从 15,384 降至 15,088 字节，RAM 从 11,920 降至
11,856 字节；原有协议、Flash 写入策略、超时和错误应答保持不变。

## 当前接收流程

ESP32 → RS485 → USART3 → DMA1 通道 1 → DMA 满传输/USART IDLE 中断 →
拼帧缓存 → CRC16 校验 → 寄存器及完整帧缓存。

- USART3 保持 1 Mbit/s、8N1；DMA 为非循环模式，关闭 RDBF 逐字节中断。
- DMA 满传输、DMA 错误、USART IDLE 和串口错误共用 `modbus_port_irq()`。
- 两块 DMA 缓冲区交替使用：先停止并读取本块，切换到另一块并重启 DMA，再处理中断中的当前块。
- DMA 与 USART3 抢占优先级均为 3，不允许互相嵌套修改组帧缓存；修改架构时应保留这个约束。
- 拼帧缓存跨 DMA 块及 IDLE 保留半帧，按协议头及长度识别完整帧；完整候选帧通过 CRC16 后才提交。
- 错误帧头、长度或 CRC16 按字节重新寻找帧头；UART/DMA 接收错误会清空半帧，丢弃至 IDLE 后恢复。
- 默认 CRC16/MODBUS：初值 FFFF、反射多项式 A001、无最终异或、低字节先发送。
  算法及字段字节序由 `modbus_config_t` 配置，需与 ESP32 一致。
- CRC32 只保存接收值，不计算或验证。
- 中断只做组帧、CRC16、字段解码及 RAM 写入，不发送应答，不写 Flash，不执行重启操作码。
  0xAA CRC16 错误会登记包号，普通上下文按协议发送 0x07 错误应答。

`main()` 已在开启接收前初始化软件状态，并在现有 OTA 状态机后调用 `modbusdeal()`。
即使普通上下文不轮询，中断也会完成寄存器更新；应用需及时取走完整帧缓存以免队列满。

## 0x10 寄存器映射

按 README 从 0x00E6 开始的 4 个寄存器数据解释：

| 寄存器 | 内容 |
| --- | --- |
| 0x00E6 | AT32 自己维护的 OTA 状态，主机不能改写 |
| 0x00E7 | 32 位会话密钥的高 16 位 |
| 0x00E8 | 32 位会话密钥的低 16 位 |
| 0x00E9 | 操作码：0 无操作，1 开始 OTA，2 重启 |

这里是 RAM 接收寄存器，不是外设寄存器或 Flash。密钥高低字由解码后的整数拆分，
线上大小端由配置独立决定。CRC16/字段格式正确的 20 字节写请求只更新 E7～E9 的密钥和操作码；
14 字节查询请求只入队，不改写缓存。操作码只保存，不立即执行。

```c
uint16_t regs[4];
if(modbus_port_read_registers(0x00E6, 4, regs) == 1)
{
    /* regs[0] 状态；regs[1]/regs[2] 密钥高低字；regs[3] 操作码。 */
}
```

该接口短暂关中断，保证读到同一次写入的一致快照，不消费帧队列。
初始化后 E6 为本地空闲状态（1），E7～E9 为零。密钥和操作码是主机请求值，不代表业务已经执行成功。

## 0x10 / 0xAA 完整帧取数

每个接收队列槽位保存一帧已完成 CRC16 校验和字段解码的数据，队列最多待处理 3 帧。
`0xAA` 没有寄存器地址字段，所以不分配虚构的保持寄存器地址，字段及固件保存在数据包缓存。

```c
static modbus_10_data_t control;
static modbus_aa_data_t packet;
static uint8_t firmware[1024];

/* 在你的架构确定后安排调用，目前不放入主循环。 */
int result = modbus_port_get_10(&control);
if(result == 1)
{
    /* 直接使用中断已经解码好的字段。 */
}
result = modbus_port_get_aa(&packet, firmware, sizeof(firmware));
if(result == 1)
{
    /* firmware[0..packet.firmware_size-1] 为本包固件。 */
}
```

- 返回 1 为成功，0 为暂无匹配数据，-1 为参数或固件缓冲区容量不足。
- 按原接收顺序取数，两个接口都要安排调用；另一类队首帧不被跳过。
- getter 只复制已处理字段及固件，不重复组帧或计算 CRC；容量不足保留帧供重试。
- 读取期间槽位保持占用，中断不会覆盖；成功复制后才释放，因此输出不依赖 DMA 内存生命周期。
- 队满时新完整帧不入队，增加 `queue_overflow`；E7～E9 仍更新为最近的有效写入值，E6 不受主机字段影响。
- 错误帧不入队、不更新寄存器，查看 `crc16_error`、`receive_error`、`frame_error`。
- `valid_frames` 为有效完整帧数，`register_writes` 为 0x10 接收寄存器更新次数。
- 取数由单一普通上下文负责，不可与自动处理接口 `modbus_port_poll()` 同时消费同一个队列。

## 发送和业务边界

### CRC16 错误应答

完整候选 0xAA 帧 CRC16 错误时不入正常队列、不改寄存器，但将包号加入独立错误队列。
调用 `modbus_port_reply_errors()` 每次发送一条 `01 AA 07 包号(2字节) CRC16(2字节)`，
包号和 CRC 字节序遵循配置，发送成功才释放记录；失败保留供下次重试。
返回 1 表示已发送，0 表示没有待发送，-1 表示发送失败。
`modbusdeal()` 统一调用该接口；两个取数接口只复制数据，不再隐式发送。
当前在你的主循环中调度 `modbusdeal()`，必须保持普通上下文周期调用才能发送错误应答。
错误队列最多保留 3 条，满时增加 `error_reply_overflow`。
0x10 错误帧仍不应答，因为现有协议没有定义控制错误应答格式。

自动处理入口 `modbus_port_poll()` 仍保留，但当前未调用。
它只消费中断校验过的完整帧，在普通上下文中运行业务回调和应答流程。
发送仍计算并追加 CRC16，PB2 拉高发送，等待 TDC 和额外 30 us 后恢复接收。

`modbus_read_10()` / `modbus_read_aa()` 是字段解码工具，本身不验证 CRC；
当前串口路径调用它们前由接收中断统一验证 CRC16，不验证 CRC32、会话密钥或包序。
`modbus_process()` 等自动业务接口也不应直接放入中断，否则会执行阻塞发送或 Flash 回调。

`upgrade.c/.h` 现已接入逐字节写入和结果检查；分区标志持久化及完整镜像激活策略仍未实现。

## AT32 设置 OTA 状态

```c
modbus_port_set_ota_status(MODBUS_STATUS_IDLE);        /* 空闲 */
modbus_port_set_ota_status(MODBUS_STATUS_DOWNLOADING); /* 下载中 */
modbus_port_set_ota_status(MODBUS_STATUS_FORBIDDEN);   /* 禁止 OTA */
uint16_t status = modbus_port_get_ota_status();
```

这些接口修改/读取的是 AT32 本地状态，与 230 寄存器和查询应答共用同一数据源。
主机请求中 ota_status 字段只保留在接收结构体中，不覆盖本地状态。
setter 只修改 RAM，不自动发送、不执行操作码；主循环保留应用状态机。
查询应答由已有协议处理函数读取本地状态生成，何时处理并发送仍由应用架构安排。
## 硬件 CRC32

`modbus_crc32(data, size)` 已切换为 AT32 CRC 外设实现，默认 CRC32 回调仍指向该函数。
当前工程已启用 CRC 模块和时钟，`main()` 调用 `wk_crc_init()` 初始化：
初值 FFFFFFFF、32 位多项式 04C11DB7、输入按字节翻转、输出全字翻转。
每次调用先 `crc_data_reset()`，按地址顺序以 8 位访问写入 `CRC->dt`，
最后 `crc_data_get() ^ 0xFFFFFFFFu`。不对输入做未对齐 32 位读取，尾部不补零。
AT32F415 手册允许 CRC_DT 使用 8/16/32 位访问：
https://www.arterytek.com/download/RM/RM_AT32F415_V2.05_EN.pdf

本函数依赖硬件初始化，不可在 PC 上直接执行，也不可与其他 CRC 外设用户并发调用。
PC 协议测试需要硬件模拟；当前完成的是字节输入数学模型和语法检查，尚未实测硬件输出。
上板验证 `modbus_crc32((const uint8_t *)"123456789", 9)` 应为 `0xCBF43926`，
长度 0 应为 0。接收中断仍只验证 CRC16，CRC32 不会因替换实现而自动启用接收校验。

## 公共处理入口 modbusdeal

`modbusdeal()` 定义在 `modbus.c`，由现有主循环状态机结束后、延时前调用。
公共操作集中在此扩展，目前包括：

1. 接收中断发现 CRC16/格式正确的 0x10 控制帧且 operation=2 时登记独立重启事件，
   `modbusdeal()` 取走后直接调用 `nvic_system_reset()`，不等待握手变量或正常队列消费。
2. 没有重启请求时发送一条待处理 0xAA CRC16 错误应答（0x07）。

错误 CRC 的重启包和查询包不会登记重启事件；重启请求优先处理。
正常握手和固件帧不由该函数消费，原 OTA 状态机继续调用 get 接口。
原主循环中读取 `handshake.operation` 后复位的分支已移除，避免使用未初始化或历史值。
## 业务设置应答码，modbusdeal 统一发送

业务调用 `modbus_set_ack(0x01, packet.packet)` 只登记应答码和包号，不操作串口。
返回 1 表示登记成功，0 表示上一条未发送（不能覆盖，稍后重试），-1 表示应答码不在 1～8。
`modbusdeal()` 按重启请求、CRC16 错误应答、业务应答的优先级处理；每次最多发送一条。
发送失败保留待发送记录，成功才清除；重复调用不会重复发送成功过的应答。
发送函数 `modbus_port_reply_aa()` 是底层执行接口，业务不应绕过 modbusdeal 直接调用。
设置函数与 modbusdeal 应由同一个普通上下文调度，不支持在中断或多个任务中并发写入。
## 新版 0xAA 固件请求（独立 L1）

`L` 现在表示整帧长度，包含两个 CRC；新增偏移 10 的 2 字节固件长度 `L1`。
必须满足 `L = L1 + 22`，当前允许 `1 <= L1 <= 1024`。

| 字段 | 偏移 | 字节数 |
| --- | --- | --- |
| 整帧长度 L | 2 | 2 |
| 协议号 | 4 | 2 |
| 密钥 | 6 | 4 |
| 固件长度 L1 | 10 | 2 |
| 总包数 | 12 | 2 |
| 当前包号 | 14 | 2 |
| 固件 | 16 | L1 |
| CRC32 | 16+L1 | 4 |
| CRC16 | 20+L1 | 2 |

结构体 `packet.data_length` 是 L，`packet.firmware_length` 是 L1，
`packet.firmware_size` 为实际复制长度，也等于 L1。get 接口及应答格式不变。
最大帧长更新为 1046 字节，DMA 每块 1047 字节，1024 字节固件输出缓冲区仍可使用。
CRC16 中断校验覆盖整帧除最后 2 字节；CRC 错误应答包号改为从偏移 14 读取。
CRC32 仅覆盖本包固件内容，共 L1 字节，不包含任何协议头或长度字段。
不再兼容旧版 L=N+10、固件偏移14的请求，ESP32 需同步升级组包逻辑。
## 声明长度与接收窗口长度

`packet.data_length`、`packet.firmware_length` 来自主机声明的 L/L1。
`packet.received_frame_size` 来自交给解码器的输入窗口字节数，
`packet.firmware_size` 从该窗口长度减 22 得到，并用作实际复制长度。
解码前已核对输入窗口与 L 相等、窗口减 22 与 L1 相等，失败不返回数据。

注意当前解析器按 L 确定帧窗口，因此这些长度不是独立于主机 L 的物理测量，
不能仅靠它们防止 CRC 碰撞。DMA 块/IDLE 段可能含半帧或多帧，不能直接当作单帧长度。
进一步的数据完整性检查应在业务中验证协议定义范围内的 CRC32、包序及镜像整体长度。
## 0x03 接收超时：3.5 ms

0x03 含义由“长度不足”改为“接收超时”，新枚举为 MODBUS_ACK_RX_TIMEOUT。
收到半帧后，接收活动停止达到 MODBUS_RX_TIMEOUT_US（3500 us）仍未完整则清理残帧。
已取得 0xAA 完整包号（至少收到前 16 字节）时，登记 0x03 和该包号，
由 modbusdeal() 使用与 0x07 相同的错误队列发送；包号不足只能丢弃，不凭旧包号应答。
DMA 继续接收、收到后续分段或已完成整帧时不触发超时。

该检查复用现有自由递减 SysTick，由 modbusdeal() 周期调用，不新增定时器中断。
阈值为 3.5 ms，检测/发送时刻受调度周期影响；现有约 1 ms 主循环可能延后约一个周期。
计时以接收事件/可观察到的 DMA 进度刷新，不作为逐字节硬件精确时间戳。
旧 MODBUS_ACK_TOO_SHORT 名称仅为源码兼容别名，自动业务中的长度错误不再冒充超时应答。
## 本次应答与升级检查修复

保持架构：接收中断组帧/CRC16/入队，业务校验/写 Flash/登记应答，modbusdeal 统一发送。

| 场景 | 当前结果 |

| 固件协议号错误 | 0x04 |
| 会话密钥错误/未建立会话 | 0x05，并将 OTA 置为禁止，需复位 |
| 当前包号不是需求包号 | 0x06 |
| 仅固件内容的 CRC32 不匹配 | 0x02 |
| 固件长度或分区容量超限 | 0x08 |

## 应用跳转交接完善

本次只修改 upgrade.c 的 intoApp 及其跳转辅助函数，不修改分区标志选择、Flash 写入、包号和主状态机。
intoApp 在普通线程且业务应答已发送后读取既有标志选择 MSP1_ADDR/MSP2_ADDR。
跳转前检查 32 KB SRAM 栈顶范围及 8 字节对齐，检查应用入口 Thumb 位及分区范围。
通过后暂停 DMA/串口、拉低 PB2、锁 Flash、停 SysTick，清 PendSV/SysTick 和全部已实现 NVIC 组，
切换 VTOR 并执行 DSB/ISB，再通过 ARMCC5/GNU 汇编桩设置 MSP/CONTROL/BASEPRI/FAULTMASK，
恢复 PRIMASK 后直接跳入 Reset_Handler，避免更换 MSP 后再访问旧 C 栈。
标志或向量无效时直接返回，不在跳转函数内阻塞通信。

应用侧必须同步确认链接地址和 SystemInit 中的向量表重定位：
app1 向量表 0x08003800（偏移 0x3800），app2 向量表 0x08012400（偏移 0x12400）。
若应用仍使用库默认 VECT_TAB_OFFSET=0，它会把 VTOR 改回 Bootloader，导致交接后的中断错误。
Bootloader 自己的 SystemInit 仍保留原配置，本次不修改其他应用工程。
