# 站号 2 与 APP 查询/重启

上位机、Bootloader 和 APP 的 OTA 管理均使用站号 2（0x02），USART3 / RS485、1M、8N1。查询和控制仍使用自定义 0x10 帧，不是标准 FC16。

APP 运行时查询返回状态 0（禁止 OTA）和 key 0；操作码 2 先发送控制确认，等待 RS485 发送完成后复位。APP 不接受开始升级和回滚操作；原标准 Modbus 业务保持不变。

新增“重启并查询OTA”：收到重启确认后每次等待 50ms，以短超时查询 Bootloader。查到允许升级状态后提示立即开始 OTA；此按钮不会延长 Bootloader 约2秒的启动窗口。

两端固件需重新编译烧录；已有合并 BIN 不会自动更新。

## 版本查询与持续压力测试

“查询版本号”显示 Flash `0x08003800` 的 OTA 版本文本和当前运行模式（Bootloader / APP）。它读取上位机写入的版本区，不使用 APP 中编译时固定的版本宏。旧固件需要先更新，才能响应版本查询。

压力测试步骤：

1. 连接串口，导入新版 `OTA.bin`。版本框自动显示文件内置版本并设为只读；只有导入纯 APP `codeBin.bin` 时可以填写版本。固件只读取一次，每轮使用该快照。
2. 设置“APP启动超时”（默认30秒，需包含 APP 上电初始化时间）和日志目录，点击“开始压力测试”。使用普通字段大端、CRC16小端、CRC32大端、首包0。
3. 从镜像头取起始版本，与设备 OTA 版本区的同段数数字版本比较后递增。四位版本保留前导零，例如 `0313 → 0314`，超出四位后自然扩展。每轮只在内存中替换1KB版本区，保留 APP 和摘要，不修改源文件；成功判定只核对 APP 模式和 OTA 版本区，不检查编译版本。
4. APP运行时自动重启并查询 Bootloader，随后握手、下载、等待 APP 回复。只有 APP模式且版本完全匹配才记为成功；Bootloader回复、100%进度、旧版本都不能算成功。
5. 失败记录阶段和原因，等待1秒后继续新一轮，不盲目重传已写入包；没有轮数上限。点击“停止压力测试”后完成当前轮再停止；关闭窗口也会等待当前轮结束。断开串口会中止当前操作。

日志目录包含同名 `.log`（带毫秒时间戳的收发明细）和 `.jsonl`（每轮目标/实际版本、耗时、成功/失败、错误及累计计数），每条记录写入后立即 flush。界面仅保留最近约5000行，磁盘保存完整测试日志。日志无法写入时停止测试并报错，避免继续执行却没有记录。

同时生成 `.commands.log` 简明指令日志：按毫秒时间戳记录发送查询、收到的运行模式/版本/OTA状态、发送重启、收到重启确认、开始升级和每轮核对结果。固件传输只记录开始与全部包确认，不逐包记录，不包含HEX、CRC及原始固件字节。详细 `.log` 和轮次 `.jsonl` 继续保留，三份日志自动同时生成，无需切换。

日志容量限制：详细日志每卷8MiB，简明日志和JSONL每卷4MiB；每类最多保留当前卷及3个旧卷（`.1`最新，`.3`最旧），一次测试合计最多64MiB。超过容量会覆盖本次最旧分卷，不再保留完整无限历史。旧测试和已有大日志不会自动删除；同目录已有日志加本次64MiB预算超过512MiB时拒绝启动。磁盘可用空间不足256MiB时停止写入并报错，运行时每秒检查一次。运行日志已加入 `.gitignore`，避免不断变化的大日志进入源码快照。

### 0x11 自定义版本查询协议

站号2，字段大端，CRC16/MODBUS低字节在前；版本区1024字节，每次读取1～32字节，范围不得超出版本区。

- 请求8字节：`02 11 | offset u16 | count u16 | CRC16`。
- 应答 `count+8` 字节：`02 11 | mode u8 | offset u16 | count u8 | 原始版本字节 | CRC16`。mode=0 为Bootloader，mode=1 为实际执行中的APP。
- 上位机按32字节读取，到NUL结束，最长1024字节，完整拼接后解码UTF-8。非法范围和CRC错误请求静默丢弃，不写Flash。

此版本回读用于确认选定镜像完成设备端校验并进入APP。它不是不同固件代码内容的身份认证：若烧录了版本头与APP不对应的工厂镜像，需要另行核对镜像来源。

# 当前固件导入方式

OTA 导入支持两种 BIN，按文件内容自动识别，普通升级和压力测试都适用：

- 原始 APP `codeBin.bin`：必须链接到 `0x08004000`，8..55296字节。上位机根据填写的版本自动补齐1KB版本区，并计算完整APP的SHA-256生成1KB摘要区，形成可传输的OTA镜像。
- Keil `OTA.bin`：保留已有摘要和APP，只填写版本区，不重复添加头部。

两种输入都不会修改源文件；不能导入 Bootloader BIN、完整烧录镜像、`appFlash.bin`（含启动记录的直烧文件）或 HEX。

## 单独导出 APP 烧录文件

点击“单独导出 APP 烧录文件…”，选择原始 `codeBin.bin` 或 Keil 的 `OTA.bin`，填写版本后导出 `appFlash.hex`（推荐）或 `.bin`。无需选择 Bootloader，无需串口连接。会重新计算原始 APP 的 SHA-256，并生成启动所需有效标记和长度记录。

| 地址 | 内容 |
| --- | --- |
| `0x08003800` | 1KB UTF-8 版本区 |
| `0x08003C00` | SHA-256 摘要32字节，其余填零 |
| `0x08004000` | 原始 APP（最多55296字节），空余填FF |
| `0x08011800` | 有效标记 `0x53484132` 和 APP 长度，两个小端32位数 |

输出范围为 `0x08003800..0x08011BFF`，共58368字节，包含完整A记录页，不包含 Bootloader 和 B备份区。**BIN 烧录地址必须设为 `0x08003800`；HEX 已含地址。设备需已有兼容 Bootloader，下载器必须使用按扇区擦除，不能全片擦除。** 此文件用于下载器直烧Flash，不是串口OTA文件；也不要交给使用全片擦除的 `flash_merged.bat`。

导入 Keil 生成的 `objects/OTA.bin`，在上位机填写版本号，然后开始 OTA。
上位机将输入的 UTF-8 版本号填入首个 1KB 版本区（剩余填零），替换文件中原版本区，
不重复增加头部；其后的 1KB SHA-256 区和 APP 原样保留，不计算 SHA-256。
版本区不参与 APP 摘要计算，设备继续验证 APP 摘要。
原始 `codeBin.bin` 现已支持自动封装；不要选择 `factory.bin`、`appFlash.bin`、HEX 或 ZIP。

以下旧说明中上位机二次打包的描述不再适用。

# AT32F415 OTA Python 桌面上位机

基于提供的 `modbus.c/h`、`upgrade.c/h`、`main.c` 的实际字节布局实现（**不是标准 Modbus FC10**）。GUI 使用 Python 标准库 tkinter，适用于 Windows。

## 启动

安装 Python 3.10+，在此目录执行：

```powershell
py -m pip install -r requirements.txt
py app.py
```

验证协议：`py -m pip install pytest` 后运行 `py -m pytest -q tests`。

## 功能

- BIN导入/保存封装镜像；1KB UTF-8 版本字符串 + 零填充；第二KB前32字节SHA-256摘要 + 992字节零填充；后接未修改的原始BIN。
- SHA-256 对完整 `raw_bin` 计算32字节摘要，放入原签名区域前32字节。设备端从 `MSPx_ADDR` 读取 `binSize-2048` 字节后核对摘要。
- 不使用数字签名、公私钥或 cryptography 依赖；此校验仅核对完整性。
- 自定义0x10查询14字节、控制20字节；0xAA数据帧 `payload+22` 字节。CRC16/MODBUS，CRC32/ISO-HDLC。默认普通字段大端、CRC16小端、CRC32大端。
- 查询状态、升级、重启、查询/无操作在线测试、离线协议自测；逐包确认应答码1与包号匹配，串口发送和接收均打印HEX。
- 可以选择串口、波特率、奇偶校验、停止位、单包字节数、会话Key、超时。波特率默认1000000（1M），预设最高1M，与当前设备配置一致。
- “查询/握手/数据应答超时(秒)”统一用于查询、开始握手、每包应答和在线测试，支持0.5等正数；不再强制握手至少15秒。操作开始前读取该值，修改不会影响已经运行的任务。
- 进度显示当前阶段、协议包号、已确认包数/总包数、已确认字节、耗时、平均速度、预计剩余时间、最近包确认耗时及串口TX/RX字节数。
- 详细日志包含分包对应的镜像区域及偏移、TX字段和完整HEX、串口写入结果、RX原始块/完整帧、拼帧缓存、CRC16错误和重同步、错包号/非预期应答、等待倒计时及失败位置。日志使用事件产生时的毫秒时间戳，可保存完整日志。
- 100%仅表示所有数据包已收到0x01应答；当前协议没有整镜像SHA-256校验及应用启动结果应答，需观察设备启动结果。

## 重要：设备端必须先确认

1. 固件校验使用SHA-256，原签名区域仍占1KB，前32字节存放摘要，余下992字节填零。
2. 哈希固定覆盖完整原始BIN，不跳过开头，不补尾部。旧签名镜像必须重新打包。
3. `upgrade.c` 中 `currentPackage` 每次开始OTA成功后清零。以实际生效的 `appUpgrade()` 路径为准：**首包号必须为 0**，`total_packets` 字段填**末包包号（包数-1）**，结束条件 `currentPackage > total_packets` 才能在收完全部包后成立。上位机默认已按此实现（GUI「首包号」默认 0）。
4. `main.c` Bootloader等待握手超时约5秒，连接前让芯片重新进入Bootloader，并立即查询；物理串口可能是USART3加RS485方向控制，需核对转接器硬件。
5. Flash空间：每个镜像分区14..69或71..126共56KB（57344字节）包含2KB头。上位机强制原始BIN在8..55296字节内；请复核具体实际地址、链接脚本和APP跳转地址。
6. 升级末包收到应答1不代表完整固件SHA-256校验和跳转已成功：上传的`appUpgrade()`流程在末包写入后校验SHA-256摘要，校验不一致仍只确认本包写入，摘要不一致也可能已经返回包成功，设备随后**静默**跳回旧 App，无错误反馈。
7. 串口CRC16校验由接收驱动（`wk_usart.c mb_assemble_byte`/`modbus_port_check_timeout`）完成；0x10 帧 CRC 错静默，0xAA 帧 CRC 错登记 ACK 0x07。在线测试只发送查询和操作码0，不发送开始OTA、重启或AA数据。

## 数据帧定义（实际C实现）

`02 AA | 整帧长度u16 | 协议号u16 | key u32 | 固件长度u16 | 总包数u16 | 当前包号u16 | 固件数据N | 固件CRC32u32 | 帧CRC16u16`

应答 `02 AA | code u8 | 当前包号u16 | CRC16u16`，共7字节。CRC32只覆盖固件数据，帧CRC16覆盖其前面的整帧内容。

## 操作建议

先做离线协议测试，修复设备端哈希长度、首包序号及SHA-256校验范围后，再用测试板进行在线查询/无操作测试，最后验证真实固件升级。上位机不会自动重传超时的数据包，避免响应丢失时重复写Flash。

新开始指令会重新擦除目标并清零会话，支持中断传输后从包0重来。状态2表示旧会话未完成，可显式重新开始；状态0仍拒绝升级。设备09也可能表示分区标志提交失败，此时不会盲目跳转。

## 固定运行 A、备份 B

APP 链接地址固定为 `0x08004000`；B 只存放备份。开始 OTA 时设备先备份有效 A，再向 A 下载；启动前校验 SHA-256，失败从 B 恢复。上位机固件封装格式不变。

新增“手动回滚”按钮发送操作码3，恢复成功收到控制应答后设备从A启动。OTA状态 `0x55` 表示两区均无有效固件，设备每100ms主动上报；该状态允许重新开始OTA修复。备份或恢复失败返回状态帧，控制等待可能超时，请结合RX状态日志判断。

首次迁移的旧镜像没有新长度记录，不能直接启动或备份，需先重新OTA安装A；下一次升级才会生成B备份。逐包100%仍不代表整镜像校验或启动成功。

## 合并 Bootloader + APP 烧录文件

在固件选择区点击“合并 Bootloader + APP 烧录文件…”，分别选择原始 `Bootloader.bin` 和原始 `APP.bin`，填写 APP 版本，再导出 `.bin` 或 `.hex`。此功能独立于串口 OTA，不需要连接串口。

- Bootloader 必须链接到 `0x08000000`，最大13KB。
- APP 必须链接到 `0x08004000`，最大55296字节；不要选择 `OTA.bin`、完整镜像或按 B 区地址链接的程序。
- 合并时计算完整原始 APP 的 SHA-256，填入 `0x08003C00`；版本放在 `0x08003800`，APP 放在 `0x08004000`。
- 在 `0x08011800` 写入有效标记 `0x53484132`，在 `0x08011804` 写入原始 APP 长度，均为小端32位。这样直接烧录后也能通过 Bootloader 启动校验。
- BIN 固定为128KB，烧录起始地址是 `0x08000000`；Intel HEX 已包含绝对地址，可由支持该格式的烧录器加载。
- 烧录时全片擦除，原 B 区备份将清除；新镜像中的 B 区和空白区均为 `0xFF`。后续 OTA 时由 Bootloader 生成备份。

串口 OTA 入口仍使用 Keil 的 `OTA.bin`，保留其中摘要。合并烧录文件不能通过“开始OTA”发送。

### 用 flash_merged.bat 烧录合并文件

仓库根目录新增 `flash_merged.bat`，沿用原 APP 工程 `flash.bat` 的 pyOCD/SWD 方式，目标 AT32F415RBT7、SWD 1MHz。不会编译工程、重新生成文件或回退下载 APP 的 AXF。

1. 接好下载器、板卡电源与 SWD。使用 under-reset 连接时还需连接 NRST。
2. 当前 Python 首次使用时安装工具（芯片算法默认复用本地 Keil 包）：

```powershell
python -m pip install pyocd
```

3. 将合并 `factory.bin` / `firmware_full.hex` 拖到根目录 `flash_merged.bat` 上；也可双击脚本选择文件，或运行：

```powershell
.
lash_merged.bat "D:\firmware\firmware_full.hex"
```

脚本先验证文件，再全片擦除、写入，成功后复位。BIN 地址固定为 `0x08000000`，HEX 使用内置地址；原 A/B 内容均会被覆盖。保留终端输出可查看错误。

仅预检、不连接或烧录设备：

```powershell
python AT32_OTA_PC/flash_merged.py "D:\firmware\factory.bin" --dry-run
```

如果使用已有 AT32 `.pack`：

```powershell
.
lash_merged.bat "D:\firmware\factory.bin" --pack "D:\packs\Keil.AT32F4xx_DFP.1.3.5.pack"
```

如果连接多个下载器，用 `python -m pyocd list --probes` 查看序列号，再向脚本附加 `--uid 序列号`。需要指定 Python 时，设置 `$env:PYOCD_PY="D:\application\python312\python.exe"`，确保该 Python 已安装 pyOCD。

本机已验证的芯片包目录为 `D:\application\KEIL\ArteryTek\AT32F415_DFP\2.1.8`，脚本会自动找到；此包的实际 pyOCD 目标名称为 `_at32f415rbt7`，脚本也会自动识别。`--pack` 既支持 `.pack` 文件，也支持含 `.pdsc` 的已安装包目录。在线 `pack install AT32F415RBT7` 没有匹配项时，无需反复运行。

## 版本与导出文件

普通升级及 OTA 导出完整保留已导入 OTA 的版本、摘要和 APP，版本框只读。只有纯 APP 可以手动填写版本。APP 分区直烧窗口导入 OTA 时也保留其内置版本。

| 默认名称 | 内容 |
| --- | --- |
| `factory.bin` | 完整 128 KiB 工厂烧录镜像 |
| `codeBin.bin` | 纯 APP，链接到 `0x08004000`，不带头和记录页 |
| `OTA.bin` | 1 KiB 版本区 + 1 KiB SHA-256 区 + 纯 APP |
| `appFlash.hex` / `.bin` | APP 分区直烧文件，带头和有效记录，BIN 起点 `0x08003800` |

新增纯 APP 导出功能可直接复制原始 APP，或从 OTA 去掉 2048 字节头；输出不会覆盖输入文件。直烧文件不可当作纯 APP 或串口 OTA。
